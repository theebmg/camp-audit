# Backups — what runs, where it goes, and how to restore

Verified 2026-10-01 by actually reading a backup and restoring a table out of it.

## What runs

`scripts/backup.sh`, from root's crontab on the camp host:

```
45 2 * * * /root/camp-audit/scripts/backup.sh >> /root/backups/backup.log 2>&1
```

**Nightly at 02:45 UTC.** One `pg_dump -Fc` of the `camp` database, gzipped.

## Where it goes

| | |
|---|---|
| **On the host** | `/root/backups/sychar-YYYY-MM-DD-HHMM.dump.gz` |
| **Off-box** | Dropbox, folder **Sychar CMMS Backup**, via `rclone` |
| **Retention** | 30 days, both places |
| **Size** | ~120 KB compressed (as of Oct 2026) |
| **Credentials** | None in the script or in git. `pg_dump` runs inside the `nocodb-db` container over its local socket; Dropbox uses rclone's own stored token. |

Dropbox is deliberately a **different provider** from DigitalOcean Spaces, which holds the
photos — so one compromised account or one fat-fingered delete cannot take both.

**Confirmed working:** 30 consecutive nightly dumps present, Sep 2 through Oct 1, each with an
`OK copied to Dropbox` line in `/root/backups/backup.log`. Every run also writes a row to
`backup_runs` and updates `system_health`, which is what the dashboard warning reads.

## What is NOT backed up

**The photos themselves.** They live in DigitalOcean Spaces, which has its own durability. This
is a deliberate scope boundary: re-photographing a building is a different order of loss from
losing condition observations that can only be regenerated by physically re-walking 337
buildings.

## How to restore

### The whole database

```bash
ssh camp
gunzip -c /root/backups/sychar-2026-10-01-0245.dump.gz > /tmp/restore.dump
docker cp /tmp/restore.dump nocodb-db:/tmp/restore.dump

# Stop the app first so nothing writes while the restore runs.
cd /root/nocodb && docker compose stop camp-audit

docker exec nocodb-db pg_restore -U camp_app -d camp --clean --if-exists /tmp/restore.dump

docker compose start camp-audit
```

From Dropbox instead, if the host is gone: `rclone copy "dropbox:Sychar CMMS Backup/<file>" .`

### One table, or just to look

This is what to reach for after an accident — it answers "what did this actually contain
before?" **without touching the live database at all**:

```bash
# print one table's rows as text, writing nothing anywhere
docker exec nocodb-db pg_restore --data-only -t board_report_items -f - /tmp/restore.dump
```

That is how the 2026-10-01 item-loss question was settled: the table was read out of the
nightly dump and compared field by field against live, proving nothing had been lost.

To restore a single table into the live database, take it to a scratch database first and copy
the rows across deliberately — `pg_restore -t` straight into `camp` appends rather than
replaces, which is rarely what is wanted. **Note:** `camp_app` cannot `CREATE DATABASE`, so a
scratch database needs a superuser role.

## Gaps worth knowing about

1. **Nothing watches the watcher.** A failed backup writes `failed` to `system_health` and the
   dashboard shows it — but only if someone looks at the dashboard. Worth an email on failure.
2. **Restores are untested end to end.** A single table has now been read out of a dump and
   verified, which is real evidence the dumps are good, but a full restore into a scratch
   database has never been rehearsed. That rehearsal is the only way to know the restore path
   works before it is needed.
3. **The window is 24 hours.** An accident at 02:44 loses a day. Fine for this workload; worth
   revisiting if the camp ever does heavy data entry.
